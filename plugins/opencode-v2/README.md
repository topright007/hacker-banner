# OpenCode Sensor V2

Плагин **0.4.1** для **OpenCode 2.0.22**. Контракт заглушки — **2.3.0**,
контракт Agent Monitor — **2.2.0**.
Поддерживается только V2. Старая реализация `plugins/opencode` для OpenCode 1.18.11
сохранена как legacy; её разработка и исправления прекращены.

По умолчанию (`backend: "stub"`) классификатор — локальная заглушка:
**всегда возвращает `deny`**. Она не оценивает
безопасность, не отправляет данные наружу и не расходует токены внешней LLM.
Адаптер заглушки находится в `src/classifier.ts`. Для Python Agent Monitor
выберите `backend: "agent_monitor"`: его настройка и строгая политика описаны ниже.
Этот backend использует доверенное CLI-подтверждение, без форм заглушки.

## Как выглядит предупреждение в режиме заглушки

В Desktop и интерактивном терминале OpenCode появляется штатная форма с тремя
короткими строками:

```text
Предупреждение: выполнение инструмента приостановлено.
Инструмент: "read"
Причина: "Тестовая заглушка отклоняет все операции; безопасность не проверялась."
```

В режиме `backend: "stub"` плагин предлагает два варианта без заранее выбранного
ответа:

1. **«Продолжить в режиме карантина»** — блокирует инструменты этой сессии и её
   дочерних сессий. Остаётся текстовое общение с LLM. Последующие вызовы отклоняются
   автоматически, без новых подтверждений и обращения к классификатору.
2. **«Довериться и продолжить»** — разрешает только показанную проверку. Для pre
   запускается конкретный инструмент; для post передаётся конкретный результат
   или ошибка. Защита остаётся включённой.

OpenCode Desktop 2.0.22 дополнительно показывает третий вариант — собственный
ответ. **Отправленный свободный текст включает тот же карантин, что и пункт 1**,
даже если написать «allow», «да» или «Довериться и продолжить».
Пустой ввод не считается ответом: форма продолжает ждать.

Скрыть собственный ответ в Desktop 2.0.22 средствами формы нельзя: интерфейс
игнорирует `custom: false`. Плагин использует `custom: true`, чтобы сервер принимал
свободный ответ и плагин мог включить карантин. Разрешающий вариант получает
случайное служебное значение, отдельное для каждой формы. API не сообщает источник
ответа: ручная отправка точного служебного значения этой формы неотличима от выбора
кнопки. Это ограничение native forms; обычный текст разрешением не считается.

Название инструмента и причина ограничены по длине и экранированы как данные.
Аргументы, полный результат, JSON контекста и stack trace в форме не показываются;
полный снимок сохраняется в локальном аудите. Форма создаётся плагином независимо
от текста LLM; её оформление и расположение определяет клиент OpenCode.

Подтверждения pre и post независимы. Поэтому после разрешения запуска заглушка
может показать вторую форму перед передачей результата. В post предупреждение
прямо сообщает, что инструмент уже выполнен: удержание результата или включение
карантина **не отменяет уже совершённые файловые, сетевые и другие действия**.

Карантин сохраняется после перезапуска OpenCode. Его наследуют существующие и
новые дочерние сессии по `parentID`. Обычная новая независимая сессия не блокируется.
Происхождение через fork само по себе не считается `parentID` и не добавляет
особого наследования карантина. Выхода из карантина через следующую форму нет.

Отмена или закрытие формы без выбранного ответа отклоняет только текущую проверку,
не включает постоянный карантин. Неотвеченная форма продолжает ждать. В режиме заглушки технические
ошибки формы, инициализации и внутренней проверки также отклоняют затронутую
операцию без переключения остальных сессий в карантин. Ошибка сохранения явно
выбранного карантина оставляет блокировку в памяти текущего процесса; долговечность
после перезапуска в этом случае не гарантируется.

## Установка готовой сборки

1. Распакуйте `opencode-sensor-v2-0.4.1.zip` в постоянную папку. Сохраните всю
   папку, включая `index.js` и `package.json`: OpenCode подключает локальную папку
   пакета. `opencode-sensor-v2.mjs` содержит runtime-зависимости и обе JSON Schema;
   отдельная установка npm-зависимостей для готовой сборки не нужна.
2. Требуется **OpenCode 2.0.22**. Проверьте `opencode --version`. При другой версии
   загруженный сенсор отменяет инструментальные операции, сохраняя текстовый диалог.
   Для CLI можно использовать `npm install -g @opencode/cli@2.0.22`; команда заменяет
   CLI в том же npm prefix. Локальный executable из раздела сборки позволяет
   проверить нужную версию без замены глобальной.
3. Добавьте элемент в массив **`plugins`** своего `opencode.json` или
   `opencode.jsonc`, сохранив остальные настройки:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    {
      "package": "/ABSOLUTE/PATH/opencode-sensor-v2-0.4.1",
      "options": {
        "enabled": true,
        "apiTimeoutMs": 5000,
        "classifierTimeoutMs": 3000
      }
    }
  ]
}
```

Замените путь на абсолютный путь к распакованной папке, например
`/Users/you/Downloads/opencode-sensor-v2-0.4.1`. В V2 нужен массив `plugins` и объект
`{package, options}`; формат V1 здесь не подходит.

4. Перезапустите фоновый сервис командой `opencode service restart` и перезапустите
   Desktop. Если Desktop установлен на macOS, а команды `opencode` нет в PATH:

```sh
"/Applications/OpenCode.app/Contents/Resources/opencode-cli" service restart
```

Для терминала используйте обычный интерактивный `opencode`, без `--standalone`.
При необходимости сначала выполните `opencode service start`.

5. Попросите агента прочитать файл и проверьте появление короткой формы внутри чата.
   Для проверки разового пропуска выберите **«Довериться и продолжить»**. Для
   проверки постоянного режима только общения используйте отдельную тестовую
   сессию и выберите **«Продолжить в режиме карантина»**.

Подключайте пакет один раз. Не загружайте V1 и V2 одновременно. Учитывайте
автоматически обнаруживаемые `.opencode/plugins` и глобальные плагины. Старые копии
сенсора перенесите за пределы каталогов discovery. Сенсор должен идти после других
плагинов, меняющих аргументы и результаты.

## Сборка из репозитория

Нужны Node.js 22+ и pnpm 11. Зависимости фиксирует `pnpm-lock.yaml`.

```sh
git clone git@github.com:topright007/hacker-banner.git
cd hacker-banner/plugins/opencode-v2
pnpm install --frozen-lockfile
pnpm build
pnpm config:print
```

Последняя команда печатает конфиг с абсолютным file URL папки пакета; manifest
указывает на `dist/index.js`. Добавьте элемент `plugins` в свой конфиг. В dev
dependencies включён OpenCode 2.0.22; запустить его можно так:

```sh
/path/to/hacker-banner/plugins/opencode-v2/node_modules/.bin/opencode /path/to/project
```

## Включение и отключение защиты

```json
{
  "package": "/ABSOLUTE/PATH/opencode-sensor-v2-0.4.1",
  "options": { "enabled": false }
}
```

- `true` или отсутствие поля: защита включена.
- JSON boolean `false`: сенсор полностью выключен — без hooks, сбора контекста,
  классификатора, форм и аудита. Штатные permissions OpenCode продолжают действовать.
- Некорректное значение, например строка `"false"`, отменяет инструментальные
  операции с ошибкой инициализации; текстовый диалог остаётся доступен.

Изменение требует перезапуска OpenCode или `opencode service restart`. Выключение
сенсора отключает и применение его карантина, но не удаляет сохранённые маркеры.
При повторном включении прежний карантин снова действует. Флаг относится только
к этому экземпляру V2 и не отключает hooks других автоматически загруженных копий.

## Подключение Agent Monitor

V2-сенсор может напрямую использовать Python-сервис из `e2e_classifier`.
Отдельный плагин `e2e_classifier/adapters/opencode` при этом подключать не нужно:
сбор контекста, audit и enforcement выполняет один `plugins/opencode-v2`.
Требуется OpenCode **2.0.22**. Python-сервис запускается отдельно и должен видеть
тот же workspace по тому же абсолютному пути.

Установите Python-пакет в отдельное окружение по инструкции `e2e_classifier/README.md`.
Из доверенного терминала, в каталоге `e2e_classifier`, запустите сервис:

```sh
umask 077
export MONITOR_ADMIN_TOKEN="$(agent-monitor token)"
agent-monitor serve
```

Сервис по умолчанию слушает `http://127.0.0.1:8765`. Его policy, SQLite database
и установка должны находиться вне изменяемого агентом workspace. При необходимости
задайте `MONITOR_POLICY` и `MONITOR_DB` абсолютными путями перед запуском.

Во втором доверенном терминале с **тем же** `MONITOR_ADMIN_TOKEN` зарегистрируйте
задачу и создайте файл credentials вне workspace; родительская приватная папка
должна уже существовать:

```sh
agent-monitor register \
  --goal "Implement the requested change in this project" \
  --workspace /absolute/task/workspace \
  --profile implement \
  --output /absolute/private/run.credentials.json
```

Для анализа без изменений используйте `--profile review`. Файл создаётся с mode
`0600`; плагин проверяет его владельца, permissions и размещение вне workspace.
Администраторский токен не входит в этот файл и не передаётся OpenCode.

Добавьте сенсор в `opencode.json` задачи:

```json
{
  "plugins": [
    {
      "package": "/ABSOLUTE/PATH/opencode-sensor-v2-0.4.1",
      "options": {
        "enabled": true,
        "backend": "agent_monitor",
        "monitorCredentials": "/absolute/private/run.credentials.json",
        "apiTimeoutMs": 5000
      }
    }
  ]
}
```

Либо напечатайте конфиг из каталога плагина:

```sh
pnpm build
pnpm config:print --monitor-credentials /absolute/private/run.credentials.json
```

Запускайте OpenCode без администраторского токена в его окружении. Monitor-режим
не использует формы OpenCode, поэтому поддерживает и приватный `--standalone`:

```sh
env -u MONITOR_ADMIN_TOKEN opencode --standalone /absolute/task/workspace
```

`backend` по умолчанию равен `stub`. Monitor-настройки без явного
`backend: "agent_monitor"` считаются ошибкой запуска. `enabled: false` отключает
весь сенсор, включая monitor. Изменение backend или credentials требует перезапуска.

В monitor-режиме:

- Pre вызывает `/v1/evaluate`. `ALLOW` требует одноразового permit, который
  потребляется через `/v1/start` непосредственно перед выполнением.
- `BLOCK` отклоняет только текущий вызов; локальный override недоступен.
  Модель может продолжить диалог или предложить другую операцию, которую сервис
  проверит заново в том же run.
- `REQUIRE_APPROVAL` удерживает исходный call ID и аргументы. ID подтверждения
  выводится в логах; оператор выполняет `agent-monitor approve APPROVAL_ID` либо
  `agent-monitor approve APPROVAL_ID --reject`. Сенсор опрашивает тот же call
  каждые 500 ms, после подтверждения получает permit и продолжает без нового
  модельного вызова. Сервис повторно проверяет policy, sensitivity epoch и expiry.
  Отклонённое или просроченное подтверждение прерывает возобновление и делает
  monitor-состояние непригодным для продолжения; зарегистрируйте новый run
  и перезапустите OpenCode с новым файлом credentials.
- Post сообщает результат или ошибку через `/v1/results`. Это обновление состояния,
  **не отдельный verdict о безопасности результата**. Встроенные pre/post формы
  заглушки в этом режиме не создаются.
- Недоступность, timeout, некорректный ответ, неполное состояние и ошибка отчёта
  блокируют текущий и последующие вызовы monitor run. Для продолжения зарегистрируйте
  новый run и перезапустите OpenCode с его credentials. Fail-open политики
  заглушки к monitor не применяется.
- Prompt/context поступают в `/v1/events` до выполнения инструментов. Максимум
  текста — 65 536 символов, JSON-запроса — 256 KiB; превышение блокирует вызов,
  без сокращения исходных данных. Полный расширенный snapshot остаётся в локальном
  audit. Monitor не анализирует всю историю или описания инструментов как LLM.

Один monitor run связан с одной сессией. Subagents, Code Mode, немедиированные
shell, prompt attachments и session subpaths не поддерживаются. Неизвестные tools
блокируются policy. Для проверенного MCP-инструмента можно задать `options.toolMap`
как точное отображение имени в настроенное имя policy; prefix автоматически не
удаляется. Нативные V2 file-tools используют аргумент `path`.

Встроенная policy запрещает shell/opaque actions, ограничивает ресурсы и destinations
и считает обычные чтения чувствительными. Эти ограничения могут остановить задачу,
которую заглушка пропускала после ручного подтверждения. Goal задаёт контекст оператору;
семантическое соответствие задаче автоматически не оценивается.

Monitor snapshots используют дополнение контракта **2.2.0**, где зафиксированы backend,
monitor run ID и fail-closed enforcement. Заглушка использует контракт **2.3.0**.
Credentials и permits не записываются в snapshots/decisions. Все ограничения
изоляции ОС и порядка hooks ниже остаются применимы.

Проверка с настоящими OpenCode и Python-сервисом, локальной scripted model и
синтетическими файлами:

```sh
# MONITOR_PYTHON — Python с зависимостями e2e_classifier.
MONITOR_PYTHON=/absolute/environment/bin/python pnpm test:monitor
```

Проверяются разрешённая запись, hard BLOCK, подтверждение/отказ, чувствительное
чтение и недоступность сервиса. Это проверка runtime enforcement, не benchmark
устойчивости реальной модели к prompt injection.

Новый выбор «Продолжить в режиме карантина» и «Довериться и продолжить»
относится только к режиму заглушки. Он не заменяет admin approval сервиса и
не обходит его BLOCK или fail-closed policy. Если у сессии уже сохранён локальный
карантин, сенсор применяет его и после переключения на Agent Monitor;
разрешение сервиса не снимает этот карантин.

## Подтверждения и ошибки в режиме заглушки

Поддерживаются Desktop 2.0.22 и интерактивный терминальный интерфейс `opencode`.
Неинтерактивный `opencode run` автоматически отменяет формы; для ручного выбора
используйте интерактивный интерфейс. Собственного HTTP-сервера сенсора, браузерной
страницы и `control.json` нет. Старый параметр `openBrowser` игнорируется.

Форма привязана к request ID, фазе, сессии и хешу неизменного снимка. Штатные
permission-запросы OpenCode остаются отдельным механизмом; их разрешения не заменяют
ответ сенсору. Таймаут, недоступность или некорректный ответ **классификатора** дают
fail-open под штатными permissions, как согласовано для MVP. Уже включённый карантин
при этом не снимается. Недоступность формы или подключения к OpenCode не считается
ошибкой классификатора и не даёт автоматического разрешения.

До выполнения блокировка возвращает `Tool.Error`. После выполнения она заменяет
весь `Tool.Result` или `Tool.Error`, включая content, structured output, metadata и
дополнительные поля. Краткий ответ инструмента также содержит только предупреждение,
инструмент и причину. Например:

```text
Предупреждение: вызов инструмента заблокирован. Режим карантина: доступен только чат; инструменты заблокированы.
Инструмент: "read"
Причина: "В сессии включён режим карантина."
```

Это содержимое результата или ошибки в карточке инструмента, доступное модели.
Плагин не вставляет отдельное сообщение ассистента; точный текст последующего
ответа LLM не гарантируется. Обычный prompt без инструментов не требует
подтверждения. Если клиент показывает `interrupted`, смотрите причину в карточке
инструмента и предшествующие сообщения `[OpenCode Sensor V2]` в логах.

### Подключение к существующему серверу

Desktop 2.0.22 и обычный терминальный `opencode` используют фоновый OpenCode service.
Сенсор автоматически обнаруживает его через официальный `Service.discover`,
проверяя PID своего процесса и версию. Дополнительный сервер не запускается;
пароль существующего сервиса не включается в запрос классификатору.

Для отдельно запущенного `opencode serve` укажите адрес этого же процесса в
`options.serverURL`, например `http://127.0.0.1:4096`, либо в переменной окружения
`OPENCODE_SENSOR_SERVER_URL`. Пароль сервера передайте через
`OPENCODE_SENSOR_SERVER_PASSWORD`; также поддерживаются `OPENCODE_PASSWORD` и
`OPENCODE_SERVER_PASSWORD`. `OPENCODE_SENSOR_SERVER_PASSWORD` сама не задаёт пароль
серверу: настройте его через `OPENCODE_PASSWORD` или `OPENCODE_SERVER_PASSWORD`.
Не помещайте пароль в конфиг плагина или чат. Разрешены только loopback-адреса.

Режим `--standalone` без известного сенсору адреса и авторизации не поддерживает
создание форм. Используйте обычный управляемый сервис. Сбой соединения или формы
отклоняет текущую операцию с объяснением, без браузерного fallback.

## Данные для классификатора

Версионированные схемы находятся в `contracts/classifier/opencode-v2`; они
сохраняют совместимость с 2.1.0/2.2.0 и добавляют 2.3.0 для нового режима заглушки.
Monitor продолжает использовать 2.2.0 со своей политикой enforcement.
Каждый локальный pre/post snapshot содержит текущий вызов, аргументы, агента и модель, результат или
ошибку, доступный контекст, время наблюдения и происхождение данных:

- Semantic snapshots `session.context` и других hooks: `system`, `messages`,
  `options`, доступные описания и JSON Schema инструментов, включая MCP.
- Registry инструментов, преобразуемые схемы, конфигурации агентов и моделей,
  доступные inventories MCP, skills, references и команд.
- `messageID`, tool call `id`, agent ID, `parentID`, метаданные сессий, permissions,
  usage/cost, location и наблюдаемое делегирование.
- Наблюдения prompt, compaction, title, generate, model/transport hooks,
  permission evaluate, событий и решений классификатора/пользователя.

Отсутствующие значения и ошибки сбора помечаются явно. Активный context API не
равен архиву сообщений до compaction. Увиденные сообщения сохраняются в памяти
плагина, но невидимую историю прошлых запусков восстановить нельзя. Полное дерево
ранее существовавших дочерних сессий также не перечисляется API плагина. Большие
semantic snapshots хранятся последними по виду запроса, без многократного полного
дублирования в журнале.

В режиме заглушки точками обращения к классификатору остаются tool pre/post. Описание MCP передаётся
вместе с контекстом; отдельной проверки каталога перед первым вызовом модели нет.
Включённый карантин блокирует следующие инструменты до этого сбора и классификации
в обоих backend. Agent Monitor получает отдельные ограниченные проекции и
результаты, как описано в разделе подключения; полный snapshot остаётся в аудите.

## Хранение и настройки

По умолчанию аудит каждого экземпляра хранится отдельно:
`~/.local/state/opencode-sensor-v2/<workspace-hash>/<instance-id>/`.

```text
requests/req_<uuid>.json   полный запрос на каждый проверенный pre/post
decisions.jsonl           решения классификатора и пользователя
```

Карантин хранится отдельно в стабильном каталоге
`~/.local/state/opencode-sensor-v2/quarantine/`, общем для экземпляров сенсора.
Имя JSON-маркера — SHA-256 идентификатора сессии; содержимое — версия схемы,
идентификатор, статус и время включения. Маркеры читаются при проверке доступа;
запись атомарная. Ошибка чтения, повреждённый маркер или недоступная цепочка родителей
блокируют затронутую операцию, не снимая защиту автоматически.

`options.stateDirectory` задаёт абсолютный путь для аудита и заменяет каталог
карантина на `<stateDirectory>/quarantine`. Для экземпляров, которые должны
применять общий карантин, используйте одно и то же хранилище карантина. При смене
этого пути старые маркеры автоматически не переносятся.

Выбор карантина записывается в аудит со `scope: "session"`; остальные собственные
решения сенсора используют `scope: "call"`. Наследование дочерними сессиями
определяется цепочкой `parentID`, а не перечислением всей истории в запросе.
`context.journal.session_gate` описывает текущее ожидание checkpoint; долговечное
состояние карантина хранится отдельно от этого снимка и журналов наблюдений.
В monitor-режиме hard BLOCK также относится к текущему вызову, а сбои сервиса,
неполное состояние и отказ возобновления approval отдельно блокируют весь run.

Новые приватные каталоги имеют права `0700`, файлы — `0600`. Credentials, auth
headers и env не извлекаются из конфигурации для классификатора. При этом исходные
prompts, аргументы и результаты могут сами содержать чувствительные данные и
сохраняются для анализа. Автоматической очистки и ротации нет. Большие сессии
увеличивают расход памяти и объём локального аудита.

## Проверки

```sh
pnpm test
pnpm typecheck
pnpm format:check
pnpm test:live
# Optional Agent Monitor integration; see setup above.
MONITOR_PYTHON=/absolute/environment/bin/python pnpm test:monitor
pnpm release
```

`test:live` запускает настоящий OpenCode 2.0.22, детерминированную локальную модель
и локальный MCP fixture. API-ключ и внешний LLM не нужны. Проверяются реальные
файловые эффекты, штатные формы и запрос модели после результата. Тест отвечает
через API формы; это не проверка кликов и внешнего вида Desktop. Нужен loopback TCP.
`release` создаёт самостоятельную сборку с инструкцией, схемами и SHA256SUMS;
для архива нужна утилита `zip`.

## Границы защиты

Это контроль локальных tool hooks внутри OpenCode, не sandbox ОС. Карантин не
прерывает уже запущенные внешние процессы и не отменяет совершённые побочные эффекты.
Параллельный инструмент может успеть выполниться до включения карантина; его
результат удерживается при следующем покрытом checkpoint. Provider-hosted tools и
действия вне этих hooks не покрываются. Поздние плагины могут менять проверенные
данные. Произвольные runtime defects и cancellation не всегда создают post hook.

Если файл плагина не загрузился или harness не зарегистрировал его hooks, плагин
не сможет ограничивать инструменты. Проверяйте активную версию и появление формы.
Снимки API собираются в разное время и не являются атомарным состоянием системы.
Модель может самостоятельно завершить ответ после ошибки инструмента: доступность
чата означает возможность следующего текстового сообщения, а не гарантированное
автоматическое продолжение текущего ответа.

[миграция V1](https://opencode.ai/v2/docs/build/plugins/migrate-v1),
[исходники v2.0.22](https://github.com/anomalyco/opencode/tree/v2.0.22/packages/plugin/src/promise).
